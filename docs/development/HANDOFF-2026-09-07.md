## 1-bis. `PRICING-PAYLOAD-CARDINALITY-HARDENING-01` — fechado (2026-09-07)

Query **`3972`** (`CREATE OR REPLACE`, ledger `20260907231143`) substituiu, em `public.get_cards_pricing_summary(p_card_ids uuid[])`, o teto `array_length(p_card_ids, 1) > 100` por `cardinality()` mais o contrato de forma `array_ndims(...) <> 1` — ambos avaliados **antes** do `RETURN QUERY` e portanto antes de qualquer `unnest`/`DISTINCT`/`LATERAL` —, deixando **zero `array_length(p_card_ids`** no corpo executável. Novo código `PRICING_SUMMARY_INVALID_PAYLOAD_SHAPE` (`ERRCODE 22023`) para um estado antes impossível de observar; as duas mensagens pré-existentes preservadas literalmente.

**Divergência de premissa corrigida antes de implementar.** O mandato citava `3903`/`3904`/`3918` como baseline, mas a definição **efetiva** no banco é a **`3968`** — escrever a correção a partir da `3918` teria **revertido silenciosamente o preço manual em produção**. Fonte primária para este tipo de correção passa a ser `pg_get_functiondef()`, não o último arquivo de migration lembrado.

Preservados: OID `56577`, assinatura, retorno de 6 colunas, `SECURITY DEFINER`/`STABLE`/owner/ACL/`search_path`, autenticação `28000`, e **toda a lógica de negócio** — provada **byte-a-byte idêntica** à `3968` (md5 `858e53ff9740b1d3f0ffff829d2986e2`).

Validação: harness **`3860`** v1.1 = **18 TOTAL / 18 PASS / 0 FAIL / 0 NOT PROVEN**. `N06` — multidimensional `dim1=2`, `cardinality=600`, rejeitado — é a prova do fechamento; `N05` sozinho passaria também com o `array_length` antigo. ## 1-ter. Registro histórico — o achado que originou o gate

*(Preservado como estava na v1.0/v1.1. O defeito descrito abaixo foi CORRIGIDO — ver §1-bis.)*

O postcheck de fechamento da Binder/Layout Foundation varreu **todas** as funções `public` com parâmetro `uuid[]` — não só as do escopo daquela frente — e encontrou um bypass real ainda vivo:

**`get_cards_pricing_summary(p_card_ids uuid[])`** — `SECURITY DEFINER`, `search_path = ''`, `owner = postgres`, `EXECUTE` para `authenticated`, negado a `anon`:

```sql
IF array_length(p_card_ids, 1) > 100 THEN          -- teto burlável
    RAISE EXCEPTION 'PRICING_SUMMARY_TOO_MANY_CARD_IDS' USING ERRCODE = '22023';
END IF;

RETURN QUERY
WITH input_ids AS (
    SELECT DISTINCT input_id FROM unnest(p_card_ids) AS input_id
), ...
```

`array_length(x, 1)` mede só a primeira dimensão. `array_fill(uuid, ARRAY[2,300])` tem `array_length(x,1) = 2` (passa pelo teto de 100) e `cardinality(x) = 600` (o que o `unnest` processa). **Mesma classe** já fechada nesta rodada em `5024`/`5046`/`5047` pelas migrations `5138`–`5140`.

**Precedente a seguir na correção:** migration incremental `CREATE OR REPLACE` (não editar `3903`/`3904`/`3918`), assinatura/retorno/segurança/grants preservados, guards `cardinality()` + `array_ndims(...) <> 1` **antes** do `unnest`, zero `array_length` no corpo executável, e harness exigindo prova comportamental com payload multidimensional. Ver `docs/05f-pricing.md`, seção de hardening de cardinalidade de `get_cards_pricing_summary(uuid[])`, e `database/proposals/2026-09-06-bulk-payload-cardinality-hardening/README.md`.

**Registrado à parte, NÃO incluir no hardening de Pricing:** `admin_decide_catalog_import_row` (guard `array_length(...,1) <> 1` burlável por array 2-D com `dim1 = 1` — defeito de contrato de entrada, sem vetor de escrita indevida em massa) e os usos que só checam `IS NULL`, sem teto algum (`admin_decide_catalog_variant_import_row`, `create_reference_based_pokedex_collection`, `set_collection_pokedex_scope`, `admin_confirm_catalog_import`, `admin_confirm_catalog_variant_import`). São **hardening de contrato `UUID[]` / admin**, em rodada própria.

**Sequência vigente (atualizada em 2026-09-07, v1.2):** Bulk Collection Operations → UX Read Models/Contracts → UX Flows/Wireframes → Frontend Collections. O gate de Pricing saiu da fila — está fechado, ver §1-bis.

WHERE l.id = p_layout_id`), com `5137` preservada como definição histórica. Mesma classe e mesma disciplina de `6109` e `6126`.

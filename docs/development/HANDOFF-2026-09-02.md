## 1. Por que este handoff existe

O handoff anterior (`HANDOFF-2026-08-28.md`) era exclusivamente documental — reconciliação da modelagem conceitual de Collections, sem nenhuma implementação física. Desde então, cinco incrementos físicos foram executados em sequência (2026-08-31 a 2026-09-02), os quatro primeiros decidindo explicitamente deixar a criação de um novo handoff para uma rodada futura ("decisão de abrir um novo handoff datado deste incremento deixada para Fabrício" — ver `README.md`, revisões `2.28`/`2.29`/`2.30`). Este documento foi criado para consolidar esse período e atualizado em linha (mesma data) para incorporar o quinto incremento (Collection Reference / Card Set Reference, `02D`).

## 2. O que foi feito desde o handoff anterior

Cinco incrementos físicos, cada um `CONFIRMADO EXECUTADO` em produção (Supabase, `qjfutqujxrbzgrtkpgkg`), todos seguindo o mesmo padrão: modelagem física em rodada própria sem alteração de banco → staging auditado em `database/proposals/` → aplicação real fase a fase, cada fase validada ao vivo antes de avançar → validação funcional (script `580X`) → performance sob volume sintético (script `580X+1`) → evidência de segurança → reconciliação de `database/schema/` e da documentação no mesmo ciclo.

1. **`COLLECTIONS-PHYSICAL-INCREMENT-01B` (2026-08-31)** — primeira fundação física: `inventory`/`physical_card`/`add_physical_cards()` (Queries `5000`–`5012`), cobrindo o núcleo patrimonial mínimo (LDM-23: 1 Inventory por User, Physical Card como exemplar individual sem `owner_user_id` direto).
2. **`COLLECTIONS-PHYSICAL-INCREMENT-02A-IMPLEMENTATION-01` (2026-09-01)** — Storage Foundation: `storage_container`/`physical_card.storage_container_id`/`create_storage_container()`/`set_physical_cards_storage()` (Queries `5020`–`5024`), pré-requisito estrutural para Collection (`collection.default_storage_container_id NOT NULL`, C-36).
3. **`COLLECTIONS-PHYSICAL-INCREMENT-02B-IMPLEMENTATION-01` (2026-09-01)** — skeleton raiz de `collection` + seis RPCs (`create_collection()`/`update_collection_metadata()`/`set_collection_default_storage()`/`archive_collection()`/`reactivate_collection()`/`delete_collection()`, Queries `5030`–`5039`), materializando LDM-12.
4. **`COLLECTIONS-PHYSICAL-INCREMENT-02C-IMPLEMENTATION-01` (2026-09-02)** — Collection Allocation: `collection_allocation`, `collection.started_at`, duas RPCs bulk-first (`allocate_physical_cards_to_collection()`/`deallocate_physical_cards_from_collection()`, Queries `5040`–`5048`), materializando LDM-07/LDM-11. Cumpre a revisão obrigatória de `delete_collection()` anunciada no incremento 3 (guarda real de C-13).
5. **`COLLECTIONS-PHYSICAL-INCREMENT-02D-IMPLEMENTATION-01` (2026-09-02)** — Collection Reference / Card Set Reference: `collection_reference`/`collection_card_set_reference` (supertipo/subtipo), `collection.mode = 'REFERENCE_BASED'` liberado fisicamente pela primeira vez, `reference_locked_at` destravado e materializado, duas RPCs (`create_reference_based_card_set_collection()`/`set_collection_card_set_reference()`, Queries `5049`–`5066`), materializando LDM-06/LDM-07/LDM-13–LDM-17. Três divergências de fixture (não de produto) identificadas e corrigidas durante a validação funcional, transparentemente documentadas.

Detalhamento completo de cada incremento (modelo físico, DDL, decisões de modelagem, validação funcional caso a caso, performance real, segurança) está em `docs/05d-colecoes-e-usuarios.md`, seções "Physical Card (Exemplar Físico) / Inventory", "Storage / Storage Container", "Collection (Coleção)", "Collection Allocation" e "Collection Reference / Card Set Reference" — não duplicado aqui. Resumo cronológico em `docs/log.md` (entradas de 2026-08-31, duas de 2026-09-01, e duas de 2026-09-02).

Nenhuma rota, componente ou linha de código de frontend foi criada em nenhum dos cinco incrementos. Nenhum commit/push foi realizado em nenhum deles.

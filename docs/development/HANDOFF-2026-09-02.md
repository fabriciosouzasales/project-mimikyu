## 1. Por que este handoff existe

Desde então, seis incrementos físicos foram executados em sequência (2026-08-31 a 2026-09-02), os quatro primeiros decidindo explicitamente deixar a criação de um novo handoff para uma rodada futura ("decisão de abrir um novo handoff datado deste incremento deixada para Fabrício" — ver `README.md`, revisões `2.28`/`2.29`/`2.30`). ## 2. O que foi feito desde o handoff anterior

Seis incrementos físicos, cada um `CONFIRMADO EXECUTADO` em produção (Supabase, `qjfutqujxrbzgrtkpgkg`), todos seguindo o mesmo padrão: modelagem física em rodada própria sem alteração de banco → staging auditado em `database/proposals/` → aplicação real fase a fase, cada fase validada ao vivo antes de avançar → validação funcional (script `58XX`) → performance sob volume sintético/real (script `58XX+1`) → evidência de segurança → reconciliação de `database/schema/` e da documentação no mesmo ciclo.

1. **`COLLECTIONS-PHYSICAL-INCREMENT-01B` (2026-08-31)** — primeira fundação física: `inventory`/`physical_card`/`add_physical_cards()` (Queries `5000`–`5012`), cobrindo o núcleo patrimonial mínimo (LDM-23: 1 Inventory por User, Physical Card como exemplar individual sem `owner_user_id` direto).
2. **`COLLECTIONS-PHYSICAL-INCREMENT-02A-IMPLEMENTATION-01` (2026-09-01)** — Storage Foundation: `storage_container`/`physical_card.storage_container_id`/`create_storage_container()`/`set_physical_cards_storage()` (Queries `5020`–`5024`), pré-requisito estrutural para Collection (`collection.default_storage_container_id NOT NULL`, C-36).
3. **`COLLECTIONS-PHYSICAL-INCREMENT-02B-IMPLEMENTATION-01` (2026-09-01)** — skeleton raiz de `collection` + seis RPCs (`create_collection()`/`update_collection_metadata()`/`set_collection_default_storage()`/`archive_collection()`/`reactivate_collection()`/`delete_collection()`, Queries `5030`–`5039`), materializando LDM-12.
4. **`COLLECTIONS-PHYSICAL-INCREMENT-02C-IMPLEMENTATION-01` (2026-09-02)** — Collection Allocation: `collection_allocation`, `collection.started_at`, duas RPCs bulk-first (`allocate_physical_cards_to_collection()`/`deallocate_physical_cards_from_collection()`, Queries `5040`–`5048`), materializando LDM-07/LDM-11. Cumpre a revisão obrigatória de `delete_collection()` anunciada no incremento 3 (guarda real de C-13).
5. **`COLLECTIONS-PHYSICAL-INCREMENT-02D-IMPLEMENTATION-01` (2026-09-02)** — Collection Reference / Card Set Reference: `collection_reference`/`collection_card_set_reference` (supertipo/subtipo), `collection.mode = 'REFERENCE_BASED'` liberado fisicamente pela primeira vez, `reference_locked_at` destravado e materializado, duas RPCs (`create_reference_based_card_set_collection()`/`set_collection_card_set_reference()`, Queries `5049`–`5066`), materializando LDM-06/LDM-07/LDM-13–LDM-17. Três divergências de fixture (não de produto) identificadas e corrigidas durante a validação funcional, transparentemente documentadas.
6. **`COLLECTIONS-PHYSICAL-INCREMENT-02E-IMPLEMENTATION-01` (2026-09-02)** — Collection Completion/Progress (`STANDARD_SET`): `collection.completion_policy` (Query `5067`, `NONE`/`STANDARD_SET`, backfill por `mode`), `create_collection()`/`create_reference_based_card_set_collection()` atualizadas para gravar a policy (Queries `5068`/`5069`), dois read models novos `SECURITY DEFINER` com ownership reconstituído manualmente (`collection_completion_summary()`/`collection_completion_positions()`, Queries `5070`/`5071` v2.0 — correção de segurança fechada ainda em staging, `-STAGING-REVISION-02`: a v1.0 originalmente proposta em `SECURITY INVOKER` retornava sempre 0 rows para qualquer Owner não-admin, por `card`/`card_variant` serem admin-only sob RLS, `ADR-022`/`ADR-030`), materializando LDM-08/LDM-20. Validação funcional real (`5810` v4.1, 72/72 casos, 0 falhas, zero resíduo pós-`ROLLBACK`) e performance real (`5811` v1.5, 9 workloads, todos < 30ms, `Function Scan`, zero leitura de disco — nenhum índice/cache/materialized view criado, sem evidência de gargalo). Dois achados reais desta rodada de implementação (distintos da correção de segurança acima, que já vinha do staging): **Achado A** — `test_results.id` é `SERIAL` e `pg_temp.log_result()` é `SECURITY INVOKER`, exigindo `GRANT USAGE ON SEQUENCE test_results_id_seq` para `authenticated`/`anon` — ausente até a primeira execução real, corrigido no próprio `5810` (v4.0→v4.1, persistido, reexecutável); **Achado B** — a ferramenta de execução SQL usada retorna só o result set do último statement de uma chamada multi-statement, contornado com duas chamadas por bateria (uma de captura, uma byte-idêntica ao arquivo com `ROLLBACK` nativo), sem alterar a lógica testada. Nenhum dos dois achados alterou `5067`–`5071`. `MASTER_SET` permanece CONCEPTUALLY READY/PHYSICALLY DEFERRED FOR SCOPE CONTROL — não implementado, não atribuído à cobertura atual do catálogo.

Detalhamento completo de cada incremento (modelo físico, DDL, decisões de modelagem, validação funcional caso a caso, performance real, segurança) está em `docs/05d-colecoes-e-usuarios.md`, seções "Physical Card (Exemplar Físico) / Inventory", "Storage / Storage Container", "Collection (Coleção)", "Collection Allocation", "Collection Reference / Card Set Reference" e "Collection Completion / Progress (02E — STANDARD_SET)" — não duplicado aqui. Resumo cronológico em `docs/log.md` (entradas de 2026-08-31, duas de 2026-09-01, e três de 2026-09-02).

Nenhuma rota, componente ou linha de código de frontend foi criada em nenhum dos seis incrementos. Nenhum commit/push foi realizado em nenhum deles.

## 3. Estado físico atual de Collections

- `inventory` / `physical_card` — CONFIRMADO EXECUTADO.
- `storage_container` / `physical_card.storage_container_id` — CONFIRMADO EXECUTADO.
- `collection` (`mode` agora `OPEN_CURATION` **ou** `REFERENCE_BASED`, imutável após criado; `visibility` ainda só `PRIVATE`; `completion_policy` materializada — ver abaixo) — CONFIRMADO EXECUTADO.
- `collection.started_at` (materializado, imutável após definido) — CONFIRMADO EXECUTADO.
- `collection_allocation` (Physical Card 0..1 Collection corrente, integridade Owner/Inventory/Game/elegibilidade de Reference) — CONFIRMADO EXECUTADO.
- `collection_reference` / `collection_card_set_reference` (supertipo/subtipo, 0..1 por Collection, CASCADE composicional, `reference_kind` fisicamente só `CARD_SET`) — CONFIRMADO EXECUTADO.
- `collection.reference_locked_at` — existia fisicamente desde o incremento 3, travado em `NULL` por CHECK; destravado no incremento 5 e materializado pela primeira Allocation de uma Collection `REFERENCE_BASED`, imutável após definido.
- `collection.completion_policy` (LDM-08, `NONE`/`STANDARD_SET`, `NOT NULL`) — **materializada nesta rodada (incremento 6, `02E`)**: `NONE` para `OPEN_CURATION`, `STANDARD_SET` para `REFERENCE_BASED`, atribuída automaticamente por `create_collection()`/`create_reference_based_card_set_collection()`. Dois read models novos, `SECURITY DEFINER` com ownership reconstituído manualmente (não-enumeração preservada): `collection_completion_summary()` (resumo agregado — total/satisfeitas/faltantes/percentual/`is_complete`) e `collection_completion_positions()` (posição a posição, com filtro `p_only_missing`). Validados por `5810`/`5811` reais — ver `docs/05d-colecoes-e-usuarios.md`, seção "Collection Completion / Progress (02E — STANDARD_SET)".
- `set_collection_visibility()`/Public Access, `created_by_user_id`/`updated_by_user_id`, `collection_pokedex_reference` (segundo subtipo de Reference), `MASTER_SET` (CONCEPTUALLY READY/PHYSICALLY DEFERRED FOR SCOPE CONTROL, nunca atribuído à cobertura atual do catálogo), e todas as demais frentes já modeladas conceitualmente (Layout, Custody & Availability, Lifecycle/Provenance, Favorite, Wishlist, Condition, Grading/Certification, Collaboration/Permissions, Activity History/Audit) — sem modelo físico.

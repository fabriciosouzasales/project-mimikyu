## 1. Resumo Executivo

Fabrício pediu a implementação do refresh diário automático de preços da fonte JustTCG (o Incremento P13 original havia excluído explicitamente esse trabalho, deixando-o para quando o pipeline de descoberta/matching de P14 estivesse maduro o suficiente — condição já satisfeita em 2026-08-21). O pedido veio decomposto em itens A–G:

- **Item A** — extrair o cliente HTTP/paginação/tipos puros da JustTCG (antes só em `scripts/sync-justtcg-pricing.ts`) para um núcleo compartilhado, reaproveitado tanto pelo CLI quanto pela nova Edge Function.
- **Item B** — núcleo puro de orquestração de UMA onda (`_shared/pricing-justtcg-refresh/`), com a mesma disciplina de dependency injection já validada para PTAX.
- **Item C** — Edge Function `justtcg-price-refresh`, mesmo padrão de adapter fino de `ptax-fx-refresh`.
- **Item D** — migration de exclusão mútua entre `CARD_SYNC` (descoberta/matching manual de P14) e `PRICE_REFRESH` (este incremento), ativos ao mesmo tempo para a mesma fonte.
- **Item E** — migration de agendamento via `pg_cron`/`pg_net`/Vault, mesmo padrão real já em produção para PTAX.
- **Item F** — bateria de testes offline obrigatórios (20+ cenários).
- **Item G** — validação completa (checks Deno, fixture-check, `git diff --check`, varredura de segredos, migrations testadas em `BEGIN`/`ROLLBACK`).

Todos os sete itens foram implementados e validados offline no mesmo ciclo. O piloto real da primeira versão, porém, revelou um incidente de produção real (ver seção 3) que exigiu uma correção estrutural antes de qualquer deploy definitivo — corrigida, testada e implantada ainda no mesmo dia.

## 3. Incidente real de produção e correção (mesmo dia)

O piloto real do primeiro desenho (`WAVE_PAGE_CAP=30`/`MAX_WAVES=10`) causou `shutdown_reason=WallClockTime` do worker da Edge Function aos ~150s (`HTTP 546`), deixando o run `6c2ca781-099d-4087-89bf-4cbd4818341c` preso em `PROCESSING` com telemetria zerada mas **2.401 `pricing_observation`/1 `pricing_product` já persistidos** antes do corte. Confirmado via Management API que o projeto Supabase está no plano Free. Uma segunda reprodução (`866ff072-0f9b-454a-873a-f989aa0aac77`, 790 observações) ocorreu quando Fabrício, por conta própria, testou manualmente a função ainda não corrigida em produção.

**Correção aplicada**:
- `WAVE_PAGE_CAP` 30→10, `MAX_WAVES` 10→30 (mesma capacidade de 300 páginas/dia, ondas menores);
- deadline interno de segurança de 110s (`deadline.ts`), verificado sempre entre Sets, nunca no meio de um;
- checkpoint incremental de telemetria por Set concluído (`checkpointTelemetry()` em `core.ts`) — garantia estrutural de nunca mais ficar preso em `PROCESSING`, mesmo sob corte inesperado do worker;
- migration `3927` reescrita para 30 jobs a cada 5 minutos, `22:30`–`00:55 UTC`.

**Três correções de segurança de log** aplicadas antes do deploy (`handler.ts`, `pricing-source-lookup.ts`, `supabase-adapter.ts`) — nenhum `error.message` cru do PostgREST chega mais a Function Logs/`pricing_sync_run.error_summary`.

**Ambos os runs presos terminalizados como `FAILED`** (`error_summary='EDGE_FUNCTION_WALL_CLOCK_TIMEOUT_PARTIAL_EXECUTION'`), preservando integralmente as escritas já confirmadas — auditoria de re-leitura imediatamente antes de cada `UPDATE` confirmou que nada havia mudado desde o diagnóstico original.

Suíte offline reescrita: 380 asserções (328 núcleo + 52 handler), incluindo cinco cenários novos provando deadline/checkpoint/idempotência — todas aprovadas via harness Node (sandbox sem runtime Deno).

## 7. Correção (2026-08-22) — Defeito Real R1/R5, Contenção Permanente, Dispatcher Durável por Set, Fechamento da Fase A

O encerramento "por completo" registrado nas seções 1–6, acima, foi prematuro. A auditoria adversarial pós-aplicação da migration `3927` (achados R1/R5) identificou risco real de duplicidade econômica: sob concorrência, a resolução de `pricing_product` podia criar duas linhas para a mesma identidade antes de qualquer uma confirmar a existência da outra.

**Contenção imediata**: os 30 jobs `justtcg-price-refresh-wave-*` foram desativados permanentemente via `cron.alter_job(active := false)` — a migration `3927` em si nunca foi revertida, só os jobs por ela criados foram desligados; permanecem `active=false` como registro histórico.

**Correção estrutural**: RPC `resolve_pricing_products_batch` elimina a janela de corrida entre leitura e criação de `pricing_product`, validada por 21 cenários de teste offline e um teste de concorrência real com duas sessões simultâneas.

**Substituição arquitetural**: em vez de reaplicar o mecanismo por ondas corrigido, foi construído o **dispatcher durável por Set** — núcleo puro `set-refresh-core.ts`, porta funcional `set-refresh-port.ts`, adapter Supabase com 3 RPCs (incluindo `open_pricing_set_refresh_attempt`, que usa lease/`lease_until` para exclusão mútua entre invocações concorrentes), Edge Function `justtcg-price-refresh-set`, migration `3934` (trigger `set_updated_at`) e migration `3935` (job `justtcg-price-refresh-set-dispatcher`, `*/5 * * * *`, `CONFIRMADO EXECUTADO`) — processando exatamente 1 Set elegível por invocação, `next_due_at` avançando ~24h a cada sucesso.

**Validação real em produção (2026-08-22)**: piloto sequencial de invocações manuais; janela controlada de 3 execuções automáticas consecutivas auditadas em profundidade; ativação definitiva do dispatcher (`active=true` permanente) com observação de um ciclo automático completo — 45/45 Sets `SUCCESS`, zero starvation, zero run órfão persistente, zero lease ativo inesperado, zero duplicidade econômica (`external_product_id`), PTAX intacto.

**Fase A — Estabilização do Pricing Refresh formalmente encerrada em 2026-08-22.** Dispatcher por Set é hoje o único mecanismo de refresh de preços JustTCG ativo em produção; os 30 jobs por onda permanecem `active=false` permanentemente. **Fase B — Resíduos de Pricing** (tratamento de `PENDING`/`NOT_FOUND`/divergências e mappings remanescentes; objetivo: nenhum `PENDING` inexplicado, `NOT_FOUND` só quando a ausência estiver comprovada) ainda não iniciada — início pendente de autorização de Fabrício.

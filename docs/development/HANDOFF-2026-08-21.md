## 1. Resumo Executivo

Fabrício pediu a implementação do refresh diário automático de preços da fonte JustTCG (o Incremento P13 original havia excluído explicitamente esse trabalho, deixando-o para quando o pipeline de descoberta/matching de P14 estivesse maduro o suficiente — condição já satisfeita em 2026-08-21). O pedido veio decomposto em itens A–G:

- **Item A** — extrair o cliente HTTP/paginação/tipos puros da JustTCG (antes só em `scripts/sync-justtcg-pricing.ts`) para um núcleo compartilhado, reaproveitado tanto pelo CLI quanto pela nova Edge Function.
- **Item B** — núcleo puro de orquestração de UMA onda (`_shared/pricing-justtcg-refresh/`), com a mesma disciplina de dependency injection já validada para PTAX.
- **Item C** — Edge Function `justtcg-price-refresh`, mesmo padrão de adapter fino de `ptax-fx-refresh`.
- **Item D** — migration de exclusão mútua entre `CARD_SYNC` (descoberta/matching manual de P14) e `PRICE_REFRESH` (este incremento), ativos ao mesmo tempo para a mesma fonte.
- **Item E** — migration de agendamento via `pg_cron`/`pg_net`/Vault, mesmo padrão real já em produção para PTAX.
- **Item F** — bateria de testes offline obrigatórios (20+ cenários).
- **Item G** — validação completa (checks Deno, fixture-check, `git diff --check`, varredura de segredos, migrations testadas em `BEGIN`/`ROLLBACK`).

Todos os sete itens foram implementados e validados offline no mesmo ciclo. O piloto real da primeira versão, porém, revelou um incidente de produção real (ver seção 3) que exigiu uma correção estrutural antes de qualquer deploy definitivo — corrigida, testada e implantada ainda no mesmo dia.

## 3. Incidente real de produção e correção (mesmo dia)

O piloto real do primeiro desenho (`WAVE_PAGE_CAP=30`/`MAX_WAVES=10`) causou `shutdown_reason=WallClockTime` do worker da Edge Function aos ~150s (`HTTP 546`), deixando o run `6c2ca781-099d-4087-89bf-4cbd4818341c` preso em `PROCESSING` com telemetria zerada mas **2.401 `pricing_observation`/1 `pricing_product` já persistidos** antes do corte. Confirmado via Management API que o projeto Supabase está no plano Free. Uma segunda reprodução (`866ff072-0f9b-454a-873a-f989aa0aac77`, 790 observações) ocorreu quando Fabrício, por conta própria, testou manualmente a função ainda não corrigida em produção.

**Correção aplicada**:
- `WAVE_PAGE_CAP` 30→10, `MAX_WAVES` 10→30 (mesma capacidade de 300 páginas/dia, ondas menores);
- deadline interno de segurança de 110s (`deadline.ts`), verificado sempre entre Sets, nunca no meio de um;
- checkpoint incremental de telemetria por Set concluído (`checkpointTelemetry()` em `core.ts`) — garantia estrutural de nunca mais ficar preso em `PROCESSING`, mesmo sob corte inesperado do worker;
- migration `3927` reescrita para 30 jobs a cada 5 minutos, `22:30`–`00:55 UTC`.

**Três correções de segurança de log** aplicadas antes do deploy (`handler.ts`, `pricing-source-lookup.ts`, `supabase-adapter.ts`) — nenhum `error.message` cru do PostgREST chega mais a Function Logs/`pricing_sync_run.error_summary`.

**Ambos os runs presos terminalizados como `FAILED`** (`error_summary='EDGE_FUNCTION_WALL_CLOCK_TIMEOUT_PARTIAL_EXECUTION'`), preservando integralmente as escritas já confirmadas — auditoria de re-leitura imediatamente antes de cada `UPDATE` confirmou que nada havia mudado desde o diagnóstico original.

Suíte offline reescrita: 380 asserções (328 núcleo + 52 handler), incluindo cinco cenários novos provando deadline/checkpoint/idempotência — todas aprovadas via harness Node (sandbox sem runtime Deno).

## 7. Correção (2026-08-22) — Defeito Real R1/R5, Contenção Permanente, Dispatcher Durável por Set, Fechamento da Fase A

O encerramento "por completo" registrado nas seções 1–6, acima, foi prematuro. A auditoria adversarial pós-aplicação da migration `3927` (achados R1/R5) identificou risco real de duplicidade econômica: sob concorrência, a resolução de `pricing_product` podia criar duas linhas para a mesma identidade antes de qualquer uma confirmar a existência da outra.

**Contenção imediata**: os 30 jobs `justtcg-price-refresh-wave-*` foram desativados permanentemente via `cron.alter_job(active := false)` — a migration `3927` em si nunca foi revertida, só os jobs por ela criados foram desligados; permanecem `active=false` como registro histórico.

**Correção estrutural**: RPC `resolve_pricing_products_batch` elimina a janela de corrida entre leitura e criação de `pricing_product`, validada por 21 cenários de teste offline e um teste de concorrência real com duas sessões simultâneas.

**Substituição arquitetural**: em vez de reaplicar o mecanismo por ondas corrigido, foi construído o **dispatcher durável por Set** — núcleo puro `set-refresh-core.ts`, porta funcional `set-refresh-port.ts`, adapter Supabase com 3 RPCs (incluindo `open_pricing_set_refresh_attempt`, que usa lease/`lease_until` para exclusão mútua entre invocações concorrentes), Edge Function `justtcg-price-refresh-set`, migration `3934` (trigger `set_updated_at`) e migration `3935` (job `justtcg-price-refresh-set-dispatcher`, `*/5 * * * *`, `CONFIRMADO EXECUTADO`) — processando exatamente 1 Set elegível por invocação, `next_due_at` avançando ~24h a cada sucesso.

**Validação real em produção (2026-08-22)**: piloto sequencial de invocações manuais; janela controlada de 3 execuções automáticas consecutivas auditadas em profundidade; ativação definitiva do dispatcher (`active=true` permanente) com observação de um ciclo automático completo — 45/45 Sets `SUCCESS`, zero starvation, zero run órfão persistente, zero lease ativo inesperado, zero duplicidade econômica (`external_product_id`), PTAX intacto.

**Fase A — Estabilização do Pricing Refresh formalmente encerrada em 2026-08-22.** Dispatcher por Set é hoje o único mecanismo de refresh de preços JustTCG ativo em produção; os 30 jobs por onda permanecem `active=false` permanentemente. **Fase B — Resíduos de Pricing** (tratamento de `PENDING`/`NOT_FOUND`/divergências e mappings remanescentes; objetivo: nenhum `PENDING` inexplicado, `NOT_FOUND` só quando a ausência estiver comprovada) ainda não iniciada — início pendente de autorização de Fabrício.

## 9. Política de Sincronização de Pricing — `pricing_refresh_policy` (2026-08-22): migrations 3937/3938

A pedido explícito de Fabrício, implementada a infraestrutura da Política de Sincronização de Pricing — configuração admin-only de frequência de refresh por `pricing_source` (1/2/3/5 dias), preparando o terreno para o Bloco 1 do Pricing Admin.

**Migration `3937`** (`CONFIRMADO EXECUTADO`): tabela `pricing_refresh_policy` (`frequency_days` restrito a `1`/`2`/`3`/`5`, seed `JUSTTCG=1`, `service_role` com apenas `SELECT`, suficiente para o `SECURITY INVOKER` de `close_pricing_set_refresh_attempt`); tabela `pricing_admin_action_log` (trilha de auditoria zero-grant, mesmo padrão de `catalog_admin_action_log`/`ADR-023`); RPCs admin `admin_set_pricing_refresh_frequency()` (upsert + auditoria + no-op guard para mudança para a mesma frequência) e `get_pricing_refresh_policy()` (leitura de todas as fontes com fallback 1 dia). `close_pricing_set_refresh_attempt()` alterado cirurgicamente só no branch `SUCCESS`: `next_due_at` passa a usar a frequência configurada na policy em vez do intervalo fixo anterior — o dispatcher por Set (`*/5 * * * *`, migration `3935`) permanece inalterado, e a política só passa a valer no **próximo** `SUCCESS` de cada Set, nunca recomputando `next_due_at` de linhas já agendadas.

**Defeito real encontrado na validação funcional pós-3937** (item 6 dos 10 pedidos por Fabrício: "1→3 gera exatamente 1 alteração + 1 audit log"): `admin_set_pricing_refresh_frequency()` continha `ON CONFLICT (pricing_source_id)` ambíguo contra a variável de saída homônima criada implicitamente por `RETURNS TABLE(pricing_source_id, ...)` — toda mudança real de frequência falhava com `42702` (o caminho no-op, que não executa o `INSERT`, mascarava o defeito). ## 19. Defeito P0 de performance em `/pricing` — diagnóstico instrumentado e correção estrutural (2026-08-23)

Fabrício reportou GETs de `/pricing` entre ~6s e ~16s em `next dev`, mesmo já compilado (um deles com `500`), e pediu diagnóstico instrumentado antes de qualquer otimização por hipótese.

**Instrumentação temporária** (`lib/perf-instrumentation.ts`, `perfMeasure`/`perfMark` gated por `PERF_DEBUG=1`) foi adicionada a 8 pontos do caminho de `/pricing` e `/catalogo` (baseline), Fabrício rodou os cenários pedidos e colou a saída real. **Removida por completo ao final desta rodada** — nenhum resíduo no repositório.

**Achado 1 — gap do middleware não é configuração**: `web/middleware.ts` não existe desde 2026-08-14 (removido por incidente de produção `MIDDLEWARE_INVOCATION_FAILED`, ver seção do próprio `docs/log.md` daquela data). `lib/supabase/middleware.ts` (`updateSession()`) ficou órfã, sem chamador real — custo zero, não contribuiu para o problema. Um comentário desatualizado em `request-auth-cache.ts` que ainda afirmava o contrário foi corrigido.

**Achado 2 — causa raiz real, com evidência**: mesmo com SQL das RPCs rápido, o request tinha 3 fases sequenciais não sobrepostas — guard de auth → `Promise.all` das 4 RPCs da página → query de `user_profile` do `Header` (~146ms fixos, toda vez, só porque `Header` só renderiza depois que a página inteira já resolveu). Em `/catalogo`, a mesma query rodava DUAS vezes por requisição (uma pelo `loading.tsx`, que também renderiza `AppShell`/`Header` reais como esqueleto — decisão da seção correspondente de 2026-08-14 — outra pela página real).

**Correção estrutural aplicada e mantida**: `getCachedUserProfile()`, novo em `lib/supabase/request-auth-cache.ts`, memoizado por `cache()` do React (mesmo padrão de `getCachedUser`/`getCachedIsAdmin`). `requirePricingAdmin()` e `requireCatalogoAdmin()` disparam essa promise (sem aguardar) logo após resolver `user`, antes das leituras específicas da página — a rede do perfil passa a rodar em paralelo com as RPCs da página em vez de depois delas. `Header` consome só `getCachedUserProfile()`, sem `createClient()` próprio. Correção vive na camada compartilhada de guard/cache, não é exclusiva de `/pricing` — beneficiou `/catalogo` (e eliminou a duplicidade) sem código extra.

**Resultado medido** (dados reais colados por Fabrício, antes/depois): warm load de `/pricing` estabilizado em ~500–600ms (era ~630–1000ms), primeiro acesso pós-compile em ~818ms; RPCs da página e `user_profile` confirmadamente em paralelo; `getCachedUser`/`getCachedIsAdmin`/`getCachedUserProfile` cada um com exatamente uma linha de log por requisição (dedupe funcionando, sem chamada duplicada). Os picos originais de 6–16s não foram reproduzidos nesta captura — por decisão explícita de Fabrício, não foram investigados além do que já foi corrigido aqui.

**Arquivos permanentes desta rodada**: `web/lib/supabase/request-auth-cache.ts` (novo `getCachedUserProfile()` + correção de comentário desatualizado), `web/components/app-shell/header.tsx` (consome `getCachedUserProfile()`), `web/components/pricing/pricing-guard.tsx`, `web/components/catalogo/catalogo-guard.tsx` (disparam `getCachedUserProfile()` cedo); `web/lib/supabase/middleware.ts` (comentário novo documentando o estado órfão, nenhuma mudança de comportamento); `docs/log.md`; este handoff. ## 21. Visão Geral — regra final do tile "Próxima atualização" (4 estados) (2026-08-23)

Ao aprovar Saúde das Fontes, Fabrício reportou uma inconsistência semântica na Visão Geral: `sets.next_due_at` (RPC `get_pricing_admin_overview`, `min()` entre Sets não pausados) pode legitimamente estar no passado mesmo com o scheduler saudável — é só o Set mais atrasado da fila, não uma previsão futura — mas o tile "Próxima atualização" (painel Atenções e Ações) mostrava esse valor cru, sugerindo atraso/quebra do dispatcher mesmo quando tudo estava operando normalmente.

**Primeira iteração**: regra de 2 estados (futuro → "Próxima atualização"; vencido + dispatcher ativo → "Atualização pendente") preservando o tratamento original para dispatcher inativo — interpretação sinalizada explicitamente a Fabrício como uma leitura possivelmente ambígua da instrução original.

**Regra final** (corrigida por Fabrício na mensagem seguinte, verbatim): nunca mostrar `next_due_at` vencido sob o rótulo "Próxima atualização", **independentemente do estado do dispatcher**. `deriveProximaAtualizacaoTile()` (`web/components/pricing/pricing-overview-stats.tsx`) reescrito com 4 estados: (1) `next_due_at` futuro → "Próxima atualização" / data formatada; (2) vencido + dispatcher ativo → "Atualização pendente" / "Aguardando processamento" (backlog normal, resolvido no próximo ciclo de 5min do cron, ver ADR-032); (3) vencido + dispatcher inativo → "Atualização atrasada" / a data vencida (agora um sinal real de problema, rótulo próprio); (4) ausente → "—", neutro.

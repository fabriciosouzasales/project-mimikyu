# Context

O Incremento P12 encerrou a exibição de preços no frontend (`ADR-029`, revisão `1.23`) com a arquitetura de sincronização e a de consulta permanecendo desacopladas por desenho: a visualização lê exclusivamente `pricing_observation` já sincronizada, nunca chama fonte externa. A sincronização de PTAX (`scripts/sync-ptax-fx-rate.ts`) e da JustTCG (`scripts/sync-justtcg-pricing.ts`) permanecia inteiramente manual — acionada localmente por Fabrício, sem nenhum mecanismo de agendamento server-side.

Discovery prévio (mesma data) confirmou por introspecção direta do runtime Supabase (`qjfutqujxrbzgrtkpgkg`): `pg_cron`/`pg_net` disponíveis mas não instalados; `supabase_vault` já habilitado; timezone do banco `UTC`; nenhuma infraestrutura de agendamento pré-existente (sem `.github/workflows`, sem Vercel Cron, sem `cron.job`); quatro Edge Functions existentes, todas com `verify_jwt = true`, nenhuma agendada; `pricing_sync_run.pricing_source_id NOT NULL` e `confirmed_by NOT NULL` — ambos incompatíveis, sem alteração, com uma execução `SCHEDULED` de PTAX (que não tem `pricing_source` nem administrador confirmando manualmente).

Fabrício aprovou explicitamente a direção arquitetural (`pg_cron`+`pg_net`+Edge Function dedicada+Vault) e um conjunto detalhado de decisões de modelagem, concorrência e auditoria, pedindo a implementação da fundação de schema (P13.1) nesta rodada — sem habilitar as extensões, sem criar Vault secret, sem Edge Function, sem chamada externa, sem tocar no script PTAX, sem nenhum código JustTCG.

# Decision

## Arquitetura-alvo para P13 (P13.2 em diante, não implementada nesta rodada)

**Supabase Cron (`pg_cron`) → `pg_net` (assíncrono, fire-and-forget) → Edge Function dedicada de PTAX → Supabase Vault** para as credenciais. `pg_net.http_post` enfileira a chamada e retorna quase imediatamente — o tempo de execução real da Edge Function nunca conta contra o limite operacional do próprio Job do Cron, o que resolve por arquitetura o requisito de "duração total inferior ao limite operacional do Cron". `cron.job_run_details` nunca substitui auditoria funcional persistente — só `pricing_sync_run`/`pricing_sync_run_call` são fonte de verdade sobre sucesso/falha real da sincronização.

## Autenticação serviço-a-serviço: secret key dedicada, nunca publishable

A Edge Function roda com `verify_jwt = false` (obrigatório — chaves no novo formato `sb_secret_...`/`sb_publishable_...` não são JWT) e valida, no próprio handler, uma secret key dedicada enviada no header `apikey` (nunca `Authorization: Bearer`, reservado a JWT real). A secret key fica exclusivamente no Vault (`vault.create_secret`), nunca em código, log ou variável de ambiente commitada. A publishable key nunca é aceita como autorização suficiente — carrega o mesmo privilégio baixo do antigo `anon`.

**Decisão de implementação**: validação manual do header `apikey` em tempo constante contra o valor decifrado do Vault, dentro do handler da Edge Function — não o pacote `@supabase/server` (padrão `auth: 'secret:<nome>'`, oficialmente documentado pelo Supabase). Mesma garantia de segurança; motivo da escolha: `@supabase/server` está em Public Beta sem versão estável fixável confirmada (sandbox sem acesso a `registry.npmjs.org` para checar), e este projeto já pratica disciplina de não introduzir dependência externa nova quando o equivalente em poucas linhas de código é auditável e não introduz risco de breaking change de um pacote ainda instável.

## Separação total entre frontend e sincronização, preservada

Nenhuma alteração desta rodada, nem da arquitetura-alvo, muda o desenho já validado no P12: visualização de preço lê só `pricing_observation`/`get_cards_pricing_summary`, nunca aciona sincronização. A Edge Function de PTAX é acionada exclusivamente pelo Cron (`SCHEDULED`) — nunca por uma rota de frontend.

## Identidade explícita de fonte cambial — `fx_source_code`, nunca `pricing_source_id` isolado

BCB/PTAX não é e não deve virar uma linha de `pricing_source` — essa tabela foi desenhada para provedores de dado de preço de carta (`default_market_scope`, `requires_commercial_agreement`, `documentation_url`, etc.), colunas que não fazem sentido para uma autoridade cambial pública nacional. `pricing_sync_run` ganha `fx_source_code TEXT`, alinhado ao mesmo domínio já usado por `pricing_fx_rate.rate_source_code` (valor real em produção: `'BCB_PTAX'`) — não uma `FK`, pelo mesmo motivo que `rate_source_code` também não é `FK`: não existe (nem deve existir) uma tabela de fontes cambiais própria neste incremento.

Regra correlacionada, aplicada como `CHECK` (`ck_pricing_sync_run_source_identity`): execuções `FX_REFRESH` têm `pricing_source_id IS NULL` e `fx_source_code IS NOT NULL`; qualquer outro `run_type` tem `pricing_source_id IS NOT NULL` e `fx_source_code IS NULL`. Nenhum estado ambíguo ou duplamente identificado é representável.

## `run_type` estendido — `FX_REFRESH`, nunca reutilizando `PRICE_REFRESH`

`PRICE_REFRESH` já tem semântica própria e consolidada (atualização de preço de carta via fonte de `pricing_source`, ex. JustTCG). Reutilizá-lo para PTAX colidiria duas semânticas distintas no mesmo valor. `ck_pricing_sync_run_type` estendido para `SET_DISCOVERY`/`CARD_SYNC`/`PRICE_REFRESH`/`FX_REFRESH`.

## `confirmed_by` opcional — `SCHEDULED` sem administrador, `MANUAL` sempre com administrador real

`admin_user` não ganha nenhuma linha sintética/de sistema — decisão explícita, alinhada a `ADR-021` (papel administrativo é sempre uma pessoa real vinculada a `auth.users`). Em vez disso, `pricing_sync_run.confirmed_by` passa a aceitar `NULL`, e uma nova regra correlacionada (`ck_pricing_sync_run_confirmed_by_by_trigger`) exige: `triggered_by = 'MANUAL' ⟹ confirmed_by IS NOT NULL`; `triggered_by = 'SCHEDULED' ⟹ confirmed_by IS NULL`. A função `validate_pricing_sync_run_confirmed_by()` (`SECURITY DEFINER`, `search_path=''`, já existente desde a correção pós-P8) passa a só consultar `admin_user` quando `NEW.confirmed_by IS NOT NULL` — quando `NULL` (sempre o caso em `SCHEDULED`, garantido pelo `CHECK` acima), a validação é dispensada por não haver o que validar. Nenhum `REVOKE`/`GRANT` da função foi alterado; `CREATE OR REPLACE` preserva o `EXECUTE` já revogado de todos os papéis.

## Concorrência: aquisição atômica por índice único parcial, nunca advisory lock

Dois índices únicos parciais, um por identidade de fonte, cobrindo os mesmos estados já considerados "ativos" pelo índice pré-existente (`ix_pricing_sync_run_active`: `RECEIVED`/`PROCESSING`):

- `ux_pricing_sync_run_active_price_per_source_type` — `(pricing_source_id, run_type) WHERE status IN ('RECEIVED','PROCESSING') AND pricing_source_id IS NOT NULL`;
- `ux_pricing_sync_run_active_fx_per_source_type` — `(fx_source_code, run_type) WHERE status IN ('RECEIVED','PROCESSING') AND fx_source_code IS NOT NULL`.

Cada índice filtra pela própria coluna `IS NOT NULL`, então nunca indexa `NULL` — diferente de `pricing_observation`/Query `3070`, `NULLS NOT DISTINCT` não é necessário aqui: não há ambiguidade de múltiplos `NULL` dentro de um índice que já exclui `NULL` por predicado. A garantia vem inteiramente do índice, válida mesmo sob PgBouncer transaction pooling — nenhuma dependência de advisory lock de conexão poolada. Estado terminal (`COMPLETED`/`COMPLETED_WITH_ERRORS`/`FAILED`/`CANCELLED`) libera automaticamente o slot para nova execução, por não satisfazer mais o predicado `WHERE`.

## JustTCG permanece inteiramente fora do P13

Nenhuma criação ou agendamento de job JustTCG nesta ADR nem no Incremento P13. `pricing_source.is_active` continua `FALSE`. A fundação de orquestração validada com PTAX (Cron/`pg_net`/Edge Function/Vault) poderá ser reaproveitada por um incremento futuro, condicionado à contratação comercial — sem nenhum código ou schema específico da JustTCG criado neste ADR.

## P13.2 — Módulo compartilhado e execução manual auditável (esta rodada)

`scripts/sync-ptax-fx-rate.ts` deixa de conter lógica de negócio própria. Toda ela foi extraída para `supabase/functions/_shared/pricing-ptax/` — núcleo puro que não lê variável de ambiente, não cria cliente Supabase e não referencia `Deno.env`/`fetch()`/`setTimeout()` do escopo global diretamente: recebe data de referência, `fetch`, função de espera e um repositório de persistência inteiramente por parâmetro (`runPtaxSync()`, em `core.ts`). O script vira um ADAPTER MANUAL fino — cria o cliente Supabase real, lê as variáveis de ambiente, resolve a data de referência em America/Sao_Paulo, e orquestra `pricing_sync_run`/`pricing_sync_run_call`. Esta mesma função `runPtaxSync()` é o ponto de reuso planejado para a Edge Function agendada de P13.3 — nenhuma lógica de busca/normalização/persistência será duplicada quando ela for implementada.

Responsabilidades do núcleo, por módulo: `period.ts` (janela padrão de exatamente 10 datas corridas inclusive — data de referência + nove dias anteriores, sem calendário de dias úteis; override explícito de início/fim para backfill manual controlado, validado em formato/ordem/tamanho máximo — `MAX_OVERRIDE_WINDOW_DAYS = 90`, decisão desta rodada); `url.ts` (construção da URL do BCB, sintaxe preservada literalmente do P9, nenhuma chamada real feita para revalidá-la nesta rodada); `http.ts` (até 3 tentativas, esperas de 1s/3s, retry só para falha de rede/timeout/408/429/5xx, nunca para os demais 4xx); `validate.ts` (validação defensiva de forma, falha funcional explícita, nunca parsing best-effort); `select-closing.ts` (seleção da cotação de fechamento por data — decisão de design registrada abaixo); `persist.ts` (persistência idempotente: só insere data ausente, taxa idêntica é `unchanged`, taxa divergente é `divergent` e nunca sobrescrita); `sync-run-orchestration.ts` (decisões puras de status final/resumo de erro, usadas pelo adapter). `sanitize.ts` centraliza a mesma disciplina de redação de segredo já usada nos conectores P8/P9, agora reaproveitada por um único módulo em vez de duplicada por script.

**Seleção de fechamento — decisão de design desta rodada**: o endpoint `CotacaoDolarPeriodo`, confirmado por chamada real em 2026-08-17 (P9), não expõe `tipoBoletim` no contrato já validado — esse campo pertence a um dataset diferente do Portal de Dados Abertos do BCB ("todos os boletins diários", `CotacaoMoedaDia`/`CotacaoMoedaPeriodo`). Ampliar `$select` para incluí-lo exigiria reconfirmar contra uma nova chamada real, fora de escopo nesta rodada ("não fazer chamada real ao BCB durante a validação"). Na ausência desse campo, `select-closing.ts` seleciona, por data, o item de `dataHoraCotacao` cronologicamente mais recente como o fechamento — correto tanto no comportamento real hoje confirmado (uma cotação por dia) quanto num cenário defensivo futuro de múltiplos boletins no mesmo dia.

**Execução manual com escrita real**: exige `--confirmed-by=<admin_user_uuid>`, mesma trigger `validate_pricing_sync_run_confirmed_by()` do restante do domínio. Abre `pricing_sync_run` com `run_type='FX_REFRESH'`, `triggered_by='MANUAL'`, `pricing_source_id=NULL`, `fx_source_code='BCB_PTAX'` — este é o PRIMEIRO efeito colateral da execução, antes de qualquer chamada ao BCB. Se outra execução `FX_REFRESH` já estiver ativa (`RECEIVED`/`PROCESSING`), o índice único parcial `ux_pricing_sync_run_active_fx_per_source_type` (`3907`) rejeita o `INSERT` com o código Postgres `23505`, e o adapter aborta imediatamente — nunca chega a tocar a rede do BCB. Cada chamada HTTP real (incluindo cada tentativa de retry) é registrada em `pricing_sync_run_call`, sem nenhuma linha artificial para divergência: `pricing_sync_run_call.error_detail` reflete só o resultado bruto da chamada HTTP em si, nunca é reescrito por causa de um achado de persistência. Divergência/item inválido só aparecem em `pricing_sync_run.error_summary` (única coluna de texto livre disponível na tabela para esse propósito) — e só quando existem: um run limpo nunca grava um resumo vazio. O run termina `COMPLETED_WITH_ERRORS` (nunca `FAILED`) quando há divergência/inválido — divergência é informação a revisar, não falha técnica; `TECHNICAL_FAILURE`/`FUNCTIONAL_FAILURE` do núcleo é que mapeiam para `FAILED`. Estado terminal é garantido em sucesso ou exceção não tratada (mesmo padrão `try/catch/finally` já usado pelo conector JustTCG desde a correção pós-P8). Modo `--dry-run` nunca cria nem finaliza `pricing_sync_run`/`pricing_sync_run_call` — nem em sucesso, nem em falha.

**Testes**: bateria de 56 asserções 100% offline (`pricing-ptax.test.ts`), cobrindo janela de 10 datas exatas, virada de mês/ano, ano bissexto, override válido/inválido, resposta válida do BCB, ausência de cotação em fim de semana, múltiplos boletins com seleção do fechamento, resposta inválida, retry/encerramento de tentativas (500×2+sucesso, 503×3 esgotando, 400 não-retryable, 429 retryable, timeout retryable), inserção nova, reexecução idempotente, taxa idêntica, taxa divergente sem overwrite, conflito concorrente antes do HTTP (classificação pura do código `23505`), estado terminal (mapeamento de resultado para status final) e ausência de segredo em `sanitize()`. Executada via Node (sandbox sem runtime Deno disponível, mesma classe de limitação já registrada para `npm run build`/`lint` em `web/`) — sintaxe confirmada válida em todos os arquivos (`node --check`), e a árvore de import real (`scripts/` → `../supabase/functions/_shared/pricing-ptax/mod.ts`) executada de ponta a ponta sob Node com um stub do pacote `npm:@supabase/supabase-js`, sem nenhum erro de resolução.

Nenhuma migration nova foi necessária — `pricing_sync_run_call` já tinha, desde `3090`, todas as colunas exigidas pelo adapter.

## P13.2 — Correção de autoridade temporal e ordenação da telemetria (auditoria pós-piloto, mesma rodada)

**Origem**: auditoria pós-piloto real do P13.2 (2026-08-18) encontrou uma execução (`pricing_sync_run.id = afeca458-7a5c-467d-80c3-49f234e608f3`) cuja `pricing_sync_run_call.called_at` aparecia 61,98s **antes** do próprio `started_at` do run ao qual pertence. Investigação somente leitura (mesma data, ciclo anterior a este) confirmou causa-raiz sistêmica: `started_at`/`finished_at` eram capturados via `new Date().toISOString()` no relógio do PROCESSO CLIENTE (máquina local de Fabrício, Windows) e gravados explicitamente, sobrescrevendo o default `now()` da coluna — enquanto `created_at`/`updated_at`/`pricing_sync_run_call.called_at` sempre usam `now()` do próprio Postgres. Qualquer desvio de relógio do cliente aparece como uma inversão temporal aparente entre essas colunas. Confirmado sistêmico nos 6 `pricing_sync_run` pré-existentes (P8/JustTCG de 2026-08-17 e P13.2/PTAX de 2026-08-18), com desvio variando 18,7s–62,0s dentro da mesma sessão — mais consistente com deriva/resync intermitente do relógio do Windows do que com um offset fixo. Os valores de `pricing_fx_rate` em si (o dado de negócio real) nunca estiveram incorretos — só a telemetria de execução.

**Decisão**: "**PostgreSQL é a autoridade dos timestamps persistidos**" de `pricing_sync_run` — nunca o relógio de nenhum processo cliente. Implementada via trigger dedicado `BEFORE INSERT OR UPDATE`, `set_pricing_sync_run_server_timestamps()` (Migration `3909`, `CONFIRMADO EXECUTADO`): todo `INSERT` recebe `started_at := now()` do servidor, independentemente do valor enviado pelo cliente; a primeira transição de status não-terminal (`RECEIVED`/`PROCESSING`) para terminal recebe `finished_at := now()` do servidor; uma vez terminal, `finished_at` torna-se imutável — atualizações posteriores preservam o valor original (`NEW.finished_at := OLD.finished_at`). Estados terminais tratados: `COMPLETED`, `COMPLETED_WITH_ERRORS`, `FAILED` (pedido explícito de Fabrício) e `CANCELLED` (incluído por consistência com `ck_pricing_sync_run_finished_consistency`, que já exige `finished_at NOT NULL` para `CANCELLED` — divergência sinalizada explicitamente antes de implementar, nunca aplicada em silêncio).

Trigger **dedicado a esta tabela** — nunca consolidado em `set_updated_at()` (função genérica compartilhada por dezenas de outras tabelas do projeto, fora de escopo desta correção). Nenhuma alteração de `GRANT`: a independência de privilégio de coluna de um trigger `BEFORE` sobre `NEW` (já demonstrada pelo próprio `set_updated_at()`, que grava em `updated_at` sem que `service_role` tenha `GRANT UPDATE` explícito nessa coluna) cobre integralmente o caso — nenhuma RPC dedicada foi necessária. Ordem de dois dos três triggers `BEFORE` de `pricing_sync_run` confirmada por `pg_trigger` (execução alfabética por nome, padrão Postgres): `trg_pricing_sync_run_server_timestamps` dispara antes de `trg_pricing_sync_run_set_updated_at`/`trg_pricing_sync_run_validate_confirmed_by`, garantindo que a `CHECK` de consistência de `finished_at` sempre veja o valor final já atribuído pelo servidor. **Nenhuma linha histórica foi alterada ou corrigida por backfill** — os 6 `pricing_sync_run` já existentes preservam o desvio de relógio já documentado; só gravações NOVAS a partir de agora são imunes a ele. A regra vale para qualquer `INSERT`/`UPDATE` futuro em `pricing_sync_run`, inclusive os do conector JustTCG (`scripts/sync-justtcg-pricing.ts`, intocado nesta rodada — protegido automaticamente pela regra do banco, sem precisar de nenhuma mudança de código nele, conforme pedido explícito de Fabrício).

**Ordenação da telemetria** (`scripts/sync-ptax-fx-rate.ts`, único adapter alterado): confirmado por leitura do código que o fluxo anterior finalizava `pricing_sync_run` (status terminal) ANTES de inserir `pricing_sync_run_call` — o run já podia aparecer `COMPLETED` no banco antes de sua telemetria de chamadas existir. Reordenado para: abrir run → executar núcleo → persistir `pricing_sync_run_call` (`persistCallLog()`, nova função) → só então finalizar o run (`finalizeSyncRun()`, refatorada, sem mais capturar `new Date()`). Se a persistência das calls falhar, o adapter finaliza o run como `FAILED` (nunca `COMPLETED`), com `error_summary` sanitizado citando a falha de persistência — garantido por um novo teste de orquestração local (fake mínimo de cliente Supabase, sem rede real).

**Reexecução idempotente confirmada estruturalmente correta, sem alteração de código**: prova nova (7 datas do piloto real, `pricing-ptax.test.ts`) e leitura de `persist.ts` confirmam `inserted=0`/`unchanged=7`/`divergent=0`/`invalid=0` e `insertRate()` nunca chamado para datas já existentes — `CONFLICT_IGNORED` é estruturalmente impossível numa reexecução idempotente normal (só ocorreria se `insertRate()` fosse de fato invocado e colidisse com uma escrita concorrente real).

**Validação**: 10/10 cenários transacionais (`BEGIN`/`ROLLBACK`) antes da aplicação real da migration `3909`, revalidados no schema real após aplicação; `get_advisors` (segurança + performance) sem nenhum achado novo relacionado a `pricing_sync_run`/à função nova (que já declara `SET search_path` explícito, evitando o alerta `function_search_path_mutable` presente em outras 4 funções não relacionadas do projeto); grants/RLS de `pricing_sync_run`/`pricing_sync_run_call` confirmados idênticos aos de antes desta rodada (nenhum `GRANT`/`REVOKE`/política alterada); 70 asserções offline (60 pré-existentes + 10 novas) revalidadas via harness Node (sandbox sem Deno), zero chamada de rede/BCB. Comandos Deno nativos (`fmt --check`/`lint`/`check`/`--fixture-check`) fornecidos a Fabrício para confirmação real local.

## P13.3 — Edge Function `ptax-fx-refresh` (esta rodada)

`supabase/functions/ptax-fx-refresh` implementada, reaproveitando `runPtaxSync()` do núcleo sem duplicar nenhuma lógica de negócio — segundo (e último planejado) chamador do módulo compartilhado, ao lado do adapter manual de P13.2. `verify_jwt = false` (`supabase/config.toml`, primeira function do projeto com esse valor, comentário explicando a fronteira de identidade real). Handler dividido em `auth.ts` (comparação manual em tempo constante do segredo, sem early return no laço — `timingSafeEqual()`) e `handler.ts` (orquestração pura e testável, dependências 100% injetadas — `index.ts` só resolve `Deno.env`/`fetch`/`createClient` reais e delega). Execução sempre `triggered_by='SCHEDULED'`, `confirmed_by=NULL`.

**Ciclo de vida de `pricing_sync_run`/`pricing_sync_run_call` extraído para reuso** (`_shared/pricing-ptax/run-lifecycle.ts`, novo módulo): `tryStartSyncRun`/`persistCallLog`/`finalizeSyncRun`/`computeReferenceDateSaoPaulo`, antes duplicados implicitamente por existirem só dentro do adapter, agora compartilhados pelos dois chamadores (`MANUAL`+`confirmedBy` ou `SCHEDULED` via um tipo `SyncRunTrigger` discriminado). `scripts/sync-ptax-fx-rate.ts` perde ~230 linhas de orquestração duplicável, sem nenhuma mudança de comportamento (70 asserções offline pré-existentes revalidadas, zero regressão).

**Correção estrutural, mesma rodada — porta funcional estreita, nunca mimese da API fluente do PostgREST**: a primeira versão de `run-lifecycle.ts` dependia de um tipo estrutural (`SupabaseLike`/`QueryBuilderLike`/`PostgrestFilterBuilderLike`) que tentava reproduzir a assinatura de `.from().select().eq()...` do `@supabase/supabase-js` real — abordagem abandonada nesta mesma rodada, antes de qualquer commit, por dois motivos confirmados: (1) `deno check` real revelou que o retorno de `.from()` é estruturalmente diferente do retorno após `.select()`/`.insert()`/`.upsert()`/`.update()`, tornando qualquer tipo estrutural único frágil contra a evolução do SDK real; (2) reproduzir uma API fluente de terceiro é, por definição, retrabalho arriscado sem benefício de domínio. Substituída por `PtaxSyncRunPort` (`interface` com cinco operações nomeadas e orientadas a domínio — `findExistingRates`/`insertRate`/`insertSyncRun`/`insertSyncRunCalls`/`updateSyncRun`, entradas/saídas sempre em tipos de domínio como `SyncRunTrigger`/`UpdateSyncRunPatch`, nunca em `{data, error}` ou nome de coluna) — `run-lifecycle.ts` depende só dela, nunca do SDK. Único implementador real: `_shared/pricing-ptax/supabase-adapter.ts` (`buildPricingPtaxSupabaseAdapter(supabase)`, novo arquivo — o único de todo `_shared/pricing-ptax/` que importa `@supabase/supabase-js`), construído exatamente uma vez por cada chamador (`scripts/sync-ptax-fx-rate.ts` e `supabase/functions/ptax-fx-refresh/index.ts`) e reaproveitado tanto como `PtaxRateRepository` (núcleo, `core.ts`) quanto como ciclo de vida do run — `PtaxSyncRunPort extends PtaxRateRepository`, então nenhum wrapper adicional existe. Zero `any`, zero cast duplo, zero supressão de lint, zero tipo recursivo em qualquer um dos arquivos tocados; os fakes de teste (CLI e Edge Function) passaram a implementar `PtaxSyncRunPort` inteiramente tipado, nunca uma fake de `SupabaseClient`/PostgREST — mudança que tornou os testes mais simples de tipar corretamente, não só um requisito formal. Validado por `tsc --strict` real (não só `node --experimental-strip-types`, que só apaga tipos e não captura erro de tipo) sobre os sete arquivos tocados, com um `tsconfig` de verificação mapeando o especificador `npm:`/bare `@supabase/supabase-js` para o pacote real já presente em `web/node_modules/`.

# Consequences

## Benefícios

- BCB/PTAX ganha identidade própria (`fx_source_code`) sem forçar uma tabela de fontes de preço de carta a representar uma autoridade cambial nacional — nenhuma coluna de `pricing_source` é distorcida ou deixada semanticamente vazia para acomodar o caso;
- execuções agendadas (`SCHEDULED`) não exigem nenhum administrador sintético nem enfraquecem a garantia já existente de que toda execução `MANUAL` tem um administrador real por trás — a regra correlacionada torna os dois casos mutuamente exclusivos e sempre corretos por construção;
- duas execuções ativas conflitantes (mesma fonte, mesmo tipo) tornam-se estruturalmente impossíveis, garantidas pelo próprio banco, não por lógica de aplicação nem por lock de conexão que poderia não sobreviver a um pooler;
- nenhuma alteração de comportamento, grant ou RLS para os fluxos já em produção (JustTCG `CARD_SYNC`/`MANUAL`) — validado por reprodução exata do formato de insert do conector real, dentro da mesma bateria de testes transacionais;
- a arquitetura-alvo aprovada (Cron/`pg_net`/Edge Function/Vault) resolve por desenho o requisito de duração/resiliência, sem depender de nenhum ajuste fino de timeout.

## Restrições / Pendências

- ~~nenhuma extensão (`pg_cron`/`pg_net`) foi habilitada até esta rodada — o agendamento real depende dessa habilitação~~ — **segue pendente, agora nomeada P13.4**: `pg_cron`/`pg_net` continuam não habilitados; nenhum Job de Cron criado; este é o próximo passo real da frente P13 (ver `docs/05f-pricing.md`, seção "Ponto de Retomada — P13.4");
